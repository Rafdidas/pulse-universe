# M2 — 직렬화와 WebSocket 전송 설계

- 작성일: 2026-09-23
- 상태: 승인 대기
- 선행: `2026-09-22-pulse-universe-contract-design.md` (계약), M1 (수집 엔진, `main` 에 병합됨)
- 범위: `SystemSnapshot` → JSON → WebSocket. 프론트엔드와 정적 파일 서빙은 제외.

## 1. 이 문서의 위치

계약서는 4개 레이어 사이의 인터페이스를 정의했고, M1은 그중 Layer 1(수집 엔진)을 구현해 `pulse-engine.exe --dump` 로 데이터 정확성을 검증했다. M2는 **Layer 2(Transport)** 를 구현한다.

계약서 4.3~4.5절이 이미 와이어 스키마를 정의하고 있으므로, 이 문서는 스키마를 다시 정의하지 않는다. 대신 그 스키마를 **어떻게 만들어 어떻게 내보낼지** — 직렬화 책임의 위치, 스레드 모델, 느린 클라이언트 처리, 실패 동작 — 를 정한다.

## 2. 측정: 페이로드 크기

설계 전에 실제 크기를 쟀다. 본 개발 PC(프로세스 360개)에서 계약서 4.4절 모양으로 스냅샷 하나를 구성하면:

```
그룹 40개 + 자식 104개 + 코어 28개  →  21,134 bytes (compact JSON)
1 Hz  →  20.6 KB/s
```

로컬호스트 루프백에서 초당 20 KB는 무시할 수 있는 양이다. **따라서 델타 프로토콜도 바이너리 포맷도 도입하지 않는다.** 계약서 4.4절이 정한 "매 주기 전체 스냅샷"을 그대로 쓴다. 프론트엔드의 파싱 비용도 1초에 20 KB이므로 문제되지 않는다.

이 수치는 그룹 수 상한(40)에 비례한다. 상한을 크게 올리거나 자식을 전부 상시 전송하도록 바꾸면 다시 재야 한다.

## 3. 확정된 결정

계약서의 D1~D6에 이어 번호를 매긴다.

| # | 결정 | 선택 | 근거 |
|---|---|---|---|
| D7 | 페이로드 형식 | 매 주기 전체 스냅샷 JSON | 2절 측정 결과 델타·바이너리가 불필요 |
| D8 | JSON 라이브러리 | Boost.JSON | Boost 를 이미 도입하므로 추가 의존성이 사실상 없음. 이스케이프·숫자 포맷이 검증된 구현 |
| D9 | 정적 파일 서빙 | **M3 로 연기** | 서빙할 프론트엔드가 아직 없어 지금 만들면 검증할 수 없다 |
| D10 | 스레드 모델 | 샘플링 전용 스레드 + io_context 스레드 | `read()` 한 번이 수백 개 프로세스 핸들을 여닫는다. io_context 에서 돌리면 수락·전송이 멈춘다 |
| D11 | 느린 클라이언트 | 세션당 대기 스냅샷 1개, 오래된 것 폐기 | 1초마다 갱신되는 데이터라 밀린 스냅샷은 보낼 가치가 없다 |

### 3.1 되돌리기 쉬운 것과 어려운 것

- **쉬움**: 포트 번호, 허용 Origin 목록, 샘플링 주기, 그룹 수 상한.
- **어려움**: D10(스레드 모델). 나중에 바꾸려면 서버와 엔진 루프를 모두 다시 짜야 한다.

## 4. 모듈 구조

```
engine/src/
  network/
    Serializer.h/.cpp        SystemSnapshot → JSON 문자열. 순수 함수. 소켓을 모른다
    WebSocketServer.h/.cpp   Beast 수락 루프, 세션 목록, 브로드캐스트
    ServerConfig.h           포트, 허용 Origin 목록
  app/
    EngineLoop.h/.cpp        샘플링 스레드. reader → aggregator → 콜백
```

기존 `core/`, `platform/`, `cli/` 는 건드리지 않는다. M1 이 만든 `SystemSnapshot` 이 그대로 입력이다.

### 4.1 책임 경계

- `Serializer` 는 `SystemSnapshot` 을 받아 문자열을 돌려준다. Boost.Asio 도 Beast 도 모른다. 순수 함수이므로 고정 스냅샷에 대한 골든 JSON 으로 단위 테스트한다.
- `WebSocketServer` 는 문자열을 받아 연결된 세션들에 보낸다. `SystemSnapshot` 이 무엇인지 모른다. 이 덕분에 나중에 다른 메시지를 얹어도 서버를 고치지 않는다.
- `EngineLoop` 는 `ISystemReader&` 와 `DataAggregator` 와 "스냅샷이 준비되면 부를 콜백" 을 받는다. WebSocket 을 모른다.
- `main` 이 셋을 엮는다.

**M2 가 `ISystemReader` 를 비로소 쓸모 있게 만든다.** M1 최종 리뷰는 이 인터페이스가 구현이 하나뿐이고 이를 통해 호출하는 곳이 없어 사실상 빈 헤더라고 지적했다. `EngineLoop` 를 가짜 리더로 테스트하려면 그 인터페이스가 필요하므로, M2 에서 경계가 실제로 사용된다.

## 5. 스레드 모델

```
메인 스레드            샘플링 스레드              io_context 스레드
  옵션 파싱
  서버 시작
  루프 시작   ────→    reader.read()
  join 대기            (수백 개 프로세스
                        핸들 여닫기)
                       aggregate()
                       serialize()
                            │
                            └── net::post ──→   세션 목록 순회
                                                 각 세션에 write
                       sleep(interval)
```

규칙:

1. **세션 목록은 io_context 스레드에서만 만진다.** 수락, 종료, 브로드캐스트가 전부 거기서 일어나므로 뮤텍스가 필요 없다. 단일 `io_context` 스레드로 운영한다 — 초당 20 KB 에 스레드 풀은 과하다.
2. **JSON 문자열은 샘플링 스레드에서 완성해서 넘긴다.** `net::post` 로 넘길 때 `std::shared_ptr<const std::string>` 로 싸서 세션들이 복사 없이 공유한다.
3. **샘플링 스레드는 서버를 모른다.** `EngineLoop` 는 `std::function<void(SystemSnapshot)>` 콜백만 호출한다. 그 콜백을 직렬화와 `post` 로 채우는 것은 `main` 의 일이다.

### 5.1 종료

`Ctrl+C` 로 종료한다. 신호 처리는 Asio 의 `signal_set` 으로 io_context 에서 받고, 샘플링 루프에는 `std::atomic<bool>` 정지 플래그를 세운 뒤 join 한다. 샘플링 스레드는 최대 한 주기(기본 1초) 안에 빠져나온다.

## 6. 메시지

계약서 4.3~4.5절이 정의한 그대로 내보낸다. 이 문서는 그 스키마를 재정의하지 않으며, 아래는 M2 에서 새로 정하는 사항만 적는다.

### 6.1 hello

연결 직후 그 세션에만 1회 보낸다. 계약서 4.3절 참조.

`core_count` 는 `ISystemReader::coreCount()` 에서, `interval_ms` 는 실행 옵션에서, `capabilities.thread_mapping` 은 M2 에서 항상 `"estimated"` 로 채운다. `host.elevated` 는 현재 프로세스 토큰의 승격 여부를 조회해 채운다 — M1 에서 비권한 실행 시 보호된 프로세스의 메모리가 0 으로 남는 것을 확인했으므로, 프론트엔드가 이 값을 보고 사용자에게 안내할 수 있어야 한다.

### 6.2 snapshot

`interval_ms` 마다 연결된 모든 세션에 보낸다. 계약서 4.4절 참조.

계약서 4.4절 예시에 있는 `type` 과 `v` 는 `SystemSnapshot` 구조체에 없다. 직렬화 시점에 `Serializer` 가 붙인다 — 구조체는 도메인 값이고 프로토콜 봉투는 전송 계층의 관심사다.

### 6.3 첫 스냅샷

연결 시점이 샘플링 주기와 무관하므로, 새 클라이언트는 `hello` 를 받은 뒤 최대 한 주기를 기다려야 첫 `snapshot` 을 받는다. **가장 최근 스냅샷을 보관했다가 `hello` 직후 즉시 보낸다.** 그러지 않으면 화면이 최대 1초 동안 비어 있다. 보관본은 io_context 스레드에서만 갱신·읽기 하므로 동기화가 필요 없다.

## 7. 느린 클라이언트

Beast 의 `async_write` 는 동시에 하나만 진행할 수 있다. 쓰기가 진행 중일 때 새 스냅샷이 오면:

- 대기 중인 스냅샷이 없으면 보관한다.
- 이미 대기 중인 것이 있으면 **새 것으로 덮어쓴다.** 큐를 키우지 않는다.

쓰기가 끝나면 대기본이 있는 경우 이어서 보낸다. 결과적으로 느린 클라이언트는 프레임을 건너뛸 뿐 뒤처지지 않는다. `seq` 가 불연속이 되지만 계약서 4.5절이 이미 그 경우 프론트엔드가 보간을 리셋하도록 정해두었다.

## 8. 보안

계약서 4.2절의 제약을 그대로 구현한다.

- 리스닝 소켓은 `127.0.0.1` 에만 바인딩한다. `0.0.0.0` 바인딩 경로를 코드에 두지 않는다.
- WebSocket 핸드셰이크에서 `Origin` 헤더를 허용 목록과 대조하고, 불일치하면 HTTP 403 으로 거절한다. 허용 목록 기본값은 개발용 Vite 주소(`http://localhost:5173`, `http://127.0.0.1:5173`)다.
- **계약은 서버 → 클라이언트 단방향이다.** 서버는 클라이언트가 보낸 프레임을 읽되 내용을 해석하지 않고 버린다. 읽기 자체는 필요하다 — 그래야 close 프레임과 연결 종료를 감지한다.

## 9. CLI 표면

`--dump` 는 그대로 유지한다. 계약서 6.3절이 말한 대로 데이터가 의심스러울 때 돌아올 검증 도구다.

```
pulse-engine --dump    [--interval-ms N] [--iterations N] [--max-groups N]
pulse-engine --json    [--interval-ms N] [--max-groups N]
pulse-engine --serve   [--port N] [--interval-ms N] [--max-groups N]
```

- `--json` 은 계약서 4.4절 형식의 JSON 하나를 표준출력에 찍고 끝낸다. 스키마를 육안으로 대조하고, 프론트엔드 없이도 페이로드를 확인하는 용도다. `--dump` 가 M1 에서 한 역할을 M2 의 산출물에 대해 한다.

  **두 번 표본을 뜨고 두 번째를 찍는다.** 계약서 6.1절대로 첫 주기에는 CPU 델타가 없어 모든 `cpu_pct` 가 `null` 로 나오는데, 그 페이로드로는 스키마의 숫자 필드를 확인할 수 없다. 따라서 한 주기를 기다렸다가 두 번째 스냅샷을 내보낸다 — `--interval-ms` 가 그 대기 시간이다. 이 모드는 `seq` 가 2 로 시작한다.
- `--serve` 가 M2 의 산출물이다. 기본 포트 9000.
- 세 모드는 상호 배타적이다. 둘 이상 지정하면 오류로 거절한다.

## 10. 실패 동작

| 상황 | 동작 |
|---|---|
| 포트가 이미 사용 중 | 어떤 포트인지 밝힌 오류 메시지 후 종료 코드 2 |
| Origin 불일치 | HTTP 403 으로 핸드셰이크 거절. 서버는 계속 동작 |
| 클라이언트 연결 끊김 | 세션만 정리하고 계속 서빙 |
| 쓰기 실패 | 해당 세션만 종료. 다른 세션에 영향 없음 |
| 샘플링 중 예외 | 로그 없이 삼키지 않는다. 메시지를 찍고 종료 코드 1 |

샘플링 스레드에서 던져진 예외는 그 스레드에서 프로세스를 끝낼 수 없다. `EngineLoop` 가 예외를 잡아 메시지를 보관하고 루프를 멈춘 뒤, 호출자가 join 후 그 메시지를 stderr 로 찍고 종료 코드 1 로 빠져나온다.

**정정 (구현 후).** 이 문단은 원래 "io_context 는 그 전에 중단시킨다" 고 적었다. **그게 틀렸다.** `WebSocketServer::stop()` 은 아무것도 동기적으로 닫지 않고 세션 정리를 io_context 에 post 할 뿐인데, `io_context::stop()` 은 큐에 남은 핸들러를 건너뛰고 `run()` 을 돌려보낼 수 있다. 그러면 정상 종료가 사라지고 클라이언트는 close code 1006 을 본다.

올바른 종료는 이렇다. **`io_context::stop()` 을 부르지 않는다.** `run()` 은 남은 작업이 없을 때 돌아오고, post 된 채 아직 실행되지 않은 핸들러도 작업으로 친다. 따라서 `stop()` 이 post 한 세션 정리는 반드시 실행된 뒤에야 `run()` 이 돌아온다. io_context 를 살려두는 것은 `signal_set` 의 대기뿐이므로 그것만 취소한다.

마지막 항목이 중요하다. 조용히 잘못된 데이터를 계속 내보내는 것이 멈추는 것보다 나쁘다 — 이 프로젝트에서 틀린 숫자는 나중에 셰이더 결함으로 위장한다.

## 11. 테스트 전략

| 대상 | 방식 |
|---|---|
| `Serializer` | 고정 `SystemSnapshot` 에 대한 골든 JSON 대조. `null` 필드, 빈 배열, 따옴표·역슬래시가 든 프로그램 이름, 한글 이름을 포함한다 |
| `Serializer` 스키마 적합성 | 출력을 Boost.JSON 으로 다시 파싱해 계약서 4.5절의 필드가 전부 있고 타입이 맞는지 확인 |
| `EngineLoop` | 가짜 `ISystemReader` 를 주입해 정해진 횟수만큼 콜백이 오는지, 정지 플래그에 반응하는지 확인 |
| `WebSocketServer` | 같은 프로세스에 Beast 클라이언트를 띄워 임시 포트로 접속. `hello` → `snapshot` 순서, 보관본 즉시 전송, Origin 거절, 클라이언트 종료 후 서버 생존을 확인 |
| 느린 클라이언트 | 클라이언트가 읽지 않는 상태에서 스냅샷을 여러 번 밀어 넣고, 큐가 자라지 않으며 마지막 것이 도착하는지 확인 |
| 전체 | `--json` 출력과 계약서 4.4절 예시를 육안 대조 |

WebSocket 테스트는 실제 소켓을 쓰되 `127.0.0.1` 의 포트 0(임시 포트)에 바인딩해 CI 와 로컬에서 충돌하지 않게 한다.

## 12. 범위 밖

- 정적 파일 서빙 (D9, M3).
- 프론트엔드 일체.
- TLS. 로컬호스트 단방향 전용이므로 불필요하다.
- 클라이언트 → 서버 명령. 계약서 4.2절이 금지한다.
- 인증. 접근 통제는 루프백 바인딩과 Origin 검사로 한다.
- ETW 기반 실측 스레드-코어 매핑. 계약서 6.2절의 정정 참조 — 데이터 모델에 자리가 없어 `RawSample` 변경이 선행되어야 한다.

## 13. 구현 순서

| # | 단계 | 완료 시 확인 가능한 것 |
|---|---|---|
| N1 | Boost 도입 + `Serializer` | `--json` 이 계약서 4.4절 형식의 JSON 을 찍는다 |
| N2 | `EngineLoop` 추출 | `--dump` 가 새 루프 위에서 동작한다. 가짜 리더로 테스트된다 |
| N3 | `WebSocketServer` | 테스트 클라이언트가 접속해 `hello` 와 `snapshot` 을 받는다 |
| N4 | `--serve` 배선 + 보관본 + 느린 클라이언트 | 브라우저 콘솔에서 1초마다 JSON 이 흐른다 |

N2 를 따로 두는 이유는, `--dump` 와 `--serve` 가 같은 샘플링 루프를 쓰게 만들어야 두 경로가 갈라지지 않기 때문이다. M1 의 `main.cpp` 는 루프를 인라인으로 갖고 있으므로 먼저 꺼낸다.

## 14. M3 이 알아야 할 것 (구현 후 추가)

M2 를 구현하면서 프론트엔드 작성자가 미리 알아야 할 사실이 몇 가지 드러났다.

**`system.cpu_pct` 는 첫 스냅샷에서도 `null` 이 아니다.** 계약서 6.1절은 "첫 주기에는 CPU 값이 없다" 고 읽히지만, 그 규칙은 델타에서 파생되는 `groups[].cpu_pct` 와 `children[].cpu_pct` 에만 적용된다. `system.cpu_pct` 는 PDH 에서 오고 수집기 생성 시점에 이미 준비되므로 숫자다(대개 0.0). 전체 렌더를 `system.cpu_pct !== null` 로 막는 프론트엔드와 그룹별로 막는 프론트엔드가 다르게 동작한다 — 후자가 와이어와 맞다.

**Origin 허용 목록은 세 곳에서 온다.** 기본값(Vite 개발 주소), 서버 자신의 origin(바인딩 직후 자동 추가 — 정적 서빙을 붙이면 브라우저가 보내는 Origin 이 바로 이것이다), 그리고 `--allow-origin` 플래그(반복 지정 가능). Vite 가 5173 대신 5174 로 밀리면 플래그로 넘긴다.

**`--json` 은 프론트엔드 없이 쓰는 도구다.** 계약 형식의 실제 페이로드를 숫자가 채워진 채로 준다. 대신 표본을 두 번 뜨므로 `--interval-ms` 만큼 기다리고, `seq` 가 2 에서 시작한다. `--iterations` 는 이 모드에서 거부된다.

**정상 종료는 close code 1000 이다.** 서버가 종료 핸드셰이크를 보내므로, 재연결 로직이 "서버가 닫았다"(1000)와 "연결이 끊겼다"(1006)를 구분할 수 있다.

**`seq` 불연속은 정상이다.** 느린 클라이언트는 프레임을 건너뛰고, 재연결하면 번호가 점프한다. 계약서 4.5절대로 보간을 리셋하면 된다.
